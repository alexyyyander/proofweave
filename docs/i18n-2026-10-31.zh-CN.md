# Proofweave 界面国际化（i18n）计划

状态：2026-10-31 收尾完成，全部公开界面双语并支持 `/zh-CN` 前缀
范围：公开站点外壳、信息页、法律支持页、登录与 Agent 连接、账户设置、个人主页、委派、评审、收据、证据与工作台的双语支持

## 1. 目标

让界面文案与代码分离，使用户可以在不改变 URL 的前提下切换语言，并让后续页面可以按命名空间逐步迁移，而不是一次性重写全部界面。

当前界面约 1,900 条可翻译字符串，分布在 81 个 `.tsx` 文件中。第一阶段不追求全量翻译，而是先建立一套可验证的机制，并完成一个可审阅的完整切片。

### 2.1 什么会翻译，什么保持原文

- **界面文案**进入词典：标题、说明、按钮、字段标签、空状态、错误信息、导航。
- **来源内容保持原文**：论文标题与摘要、上游命题、目录中的问题陈述、学科名称、模型起草的解释正文与术语定义。它们是固定快照的一部分，翻译会改变可复核的对象。
- **历史里程碑**：界面与时间线进入词典；22 条史料的标题、摘要、AI/人类贡献、证据与边界放在 [`app/history/milestone-copy.ts`](../app/history/milestone-copy.ts)，未翻译条目会回退英文原文。
- 首页与 `/explore` 中的目录记录标题、陈述来自数据库，同样保持原文。

### 2.2 验证数据的本地化

`verifyBuildWeekDemoFixture()` 接受可选 `locale`，在生成证据对象时使用对应词典。首页、`/demo` 与 `/api/demo/verify` 都传入当前 locale（API 从请求 cookie 或 `Accept-Language` 读取）。因此检查标题、说明、结果、旅程叙述、执行边界、信用预览与披露文本会随语言切换，而哈希、ID、时间戳与协议版本保持原样。

## 3. 架构决策

### 3.1 零依赖、类型化词典

不引入 `next-intl`、`react-i18next` 等运行时。词典是普通 TypeScript 对象：

- `app/i18n/dictionaries/en.ts` 是唯一的事实来源，`TranslationKey` 由它的键推导。
- `app/i18n/dictionaries/zh-CN.ts` 的类型是完整的 `Dictionary`，缺少任何键都会让 `npm run typecheck` 失败。
- 键使用扁平点号命名（`about.topic.principles.title`），词典内容是纯字符串，便于后续交给翻译流程或导出为 JSON。
- `translate()` 支持 `{name}` 插值；缺失变量会原样保留，避免渲染 `undefined`。

### 3.2 Locale 解析顺序

`app/i18n/server.ts` 的 `getLocale()` 每个请求只执行一次（React `cache`）：

1. 中间件注入的 `x-pw-locale` 请求头（来自 `/zh-CN` 前缀，或中间件对无前缀请求协商出的语言）；
2. `pw_locale` cookie（用户显式选择）；
3. `Accept-Language`（`zh`、`zh-Hans`、`zh-TW` 等统一映射到 `zh-CN`）；
4. 默认 `en`。

前缀优先级最高，因此直接访问 `/zh-CN/...` 总会渲染中文，即使浏览器的 cookie 仍是英文。

`getI18n()` 返回 `{ locale, dictionary, t }`，服务端组件直接使用：

```tsx
const { t } = await getI18n();
<SectionTitle>{t("about.title")}</SectionTitle>
```

客户端组件从根布局的 `I18nProvider` 获取：

```tsx
"use client";
const { t, locale } = useI18n();
```

当前客户端 Provider 会收到整份词典。词典规模变大后，应按页面或命名空间拆分后再传入，避免把无关文案发送到浏览器。

### 3.3 URL 前缀与中间件

中文使用真实 URL 前缀 `/zh-CN/...`，英文继续使用无前缀 URL。实现采用根目录 [`middleware.ts`](../middleware.ts)：

- `/zh-CN/...` 在内部重写到现有路由，并注入 `x-pw-locale` 与 `x-pw-pathname` 请求头，浏览器地址栏保持 `/zh-CN/...`；
- 未带前缀的请求如果 cookie 或 `Accept-Language` 选择中文，返回 307 到 `/zh-CN/...`，因此中文页面里的无前缀内部链接也会落在前缀 URL 上；
- `/api`、`/auth`、`/authorize`、`/mcp`、`/token`、`/start`、`/_next` 等非页面路由、点开头目录（如 `/.well-known`）与静态资源扩展名不参与前缀重写；只有 `GET`/`HEAD` 会被重定向到前缀，其他方法保留原 URL，仅注入 locale 头；
- 非页面清单集中在 [`app/i18n/routing.ts`](../app/i18n/routing.ts)，中间件的 `config.matcher` 与请求内检查都由同一份清单生成，避免两处规则漂移；
- 中间件同时写入 `pw_locale` cookie，使后续请求保持语言，并注入 `x-pw-return-path`（当前路径与查询串）供语言菜单使用。

页面文件不需要移动到 `app/[locale]/`，英文 URL、现有链接和渲染测试保持稳定。代价是中文页面的内部链接需要一次 307 才能到达前缀 URL；这由中间件统一处理，不要求逐页改写链接。

### 3.3.1 规范化与 hreflang

根布局从 `x-pw-pathname` 推导当前路径，为每个页面输出：

- `<link rel="canonical">`：英文无前缀，中文 `/zh-CN/...`；
- `<link rel="alternate" hreflang="en">`、`hreflang="zh-CN"` 与 `hreflang="x-default"`；
- `og:locale` 与 `og:locale:alternate`。

### 3.4 客户端词典裁剪

[`app/i18n/client-dictionary.ts`](../app/i18n/client-dictionary.ts) 维护两层过滤：

- `clientDictionaryPrefixes`：所有可能进入客户端 bundle 的命名空间，用于守卫测试；服务端专属文案不会进入 RSC payload。
- `clientDictionaryGroups`：按路由首段分组的命名空间。根布局只传 `common.` 核心词条，[`app/template.tsx`](../app/template.tsx) 在每次导航时按 `x-pw-pathname` 选择该区块的词典再传给 `I18nProvider`。template 的存在保证从 `/explore` 客户端跳转到 `/workbench` 时词典会随之替换，而不是沿用根布局的旧词典。

按区块裁剪后，首页只携带 `showcase.`（约 6 KB），`/publications` 约 0.2 KB，`/explore` 约 21 KB；工作台仍需要约 67 KB 的合并命名空间。词典按 locale 缓存（`WeakMap`），同一请求内不会重复过滤。

新增使用 `useI18n()` 的组件时，需要把其命名空间前缀加入 `clientDictionaryPrefixes`，并加入该组件出现页面对应的 `clientDictionaryGroups` 条目；`tests/ui/i18n.test.tsx` 会检查分组引用的前缀都存在，渲染测试会验证中文区块的文字没有退化成键名。

### 3.5 语言切换

语言菜单是服务端组件，每个选项都是普通链接，并携带中间件注入的 `next` 参数（当前路径与查询串）：

```
/api/locale?to=zh-CN&next=%2Fabout
```

`app/api/locale/route.ts` 校验目标语言、写入 `HttpOnly` cookie（`Path=/; Max-Age=1 年; SameSite=Lax`，HTTPS 下加 `Secure`），然后 303 跳回 `next`（不可用时回退 `Referer`，最后 `/`）。不依赖客户端 JavaScript，禁用它也能切换语言；即使浏览器策略不发送 `Referer`，也会回到当前页面。

## 4. 目录结构

```text
app/i18n/
  config.ts                 locale 列表、cookie 名、Accept-Language 协商
  routing.ts                非页面路由与静态资源判定（中间件共享）
  translate.ts              翻译函数与 Dictionary 类型
  server.ts                 getLocale / getI18n（仅服务端）
  client.tsx                I18nProvider / useI18n（仅客户端）
  LocaleSwitcher.tsx        页头语言菜单（服务端渲染）
  dictionaries/
    en.ts                   英文基准与 TranslationKey
    zh-CN.ts                简体中文
    index.ts                locale → dictionary
app/api/locale/route.ts     持久化语言选择并跳回
app/template.tsx            按路由区块提供客户端词典
tests/ui/i18n.test.tsx      词典完整性、占位符、locale 协商测试
```

样式位于 `app/components/shell/site-frame.css` 的 `.locale-menu` 区块。

## 5. 新增文案的流程

1. 在 `dictionaries/en.ts` 末尾加入英文键值；英文默认输出必须与现有界面逐字一致，避免破坏渲染测试。
2. 在同一位置为 `zh-CN.ts` 补上对应键；`npm run typecheck` 会检查缺失键。
3. 服务端组件用 `t("key")`；客户端组件用 `useI18n()`。
4. 数据数组不要硬编码文案，改为 `{ titleKey, copyKey, href }` 之类的键引用，见 `app/about/page.tsx`。
5. 运行 `npm run typecheck` 与 `npm run i18n:check`。

共享组件约束：`app/components/` 下的非 `shell` 组件不能直接依赖 `app/i18n`（`scripts/ui/audit-components.mjs` 会判定为越层依赖）。这类组件应继续接收已翻译的字符串或键作为 props，由页面或客户端模块负责调用 `t()`。

## 7. 验证

```bash
npm run typecheck
npm run i18n:check
npm run ui:check
npm run build
node --test --test-concurrency=1 --test-name-pattern="localized" tests/rendered-html.test.mjs
```

`npm run i18n:check` 覆盖词典完整性、占位符一致性、locale 协商，以及 `pathForLocale` / `stripLocalePrefix` 对 `/`、`/zh-CN`、`/zh-CN/about` 的规范化。它同时属于 `npm run ui:check`，而 CI 的 `check` 与 `check:fast` 现在都会运行 `ui:check`，因此词典与客户端命名空间守卫不会只停留在本地。

`rendered-html.test.mjs` 中新增的用例验证：

- `/zh-CN/...` 直接返回中文并保留前缀 URL；
- 未带前缀的请求在 cookie 或 `Accept-Language` 选择中文时 307 到 `/zh-CN/...`；
- 中文页面输出 canonical `/zh-CN/...` 与 `hreflang` 英文/中文/x-default 链接；
- 首页的证明旅程、证据检查标签与验证控制台随语言切换；
- `Accept-Language: zh-CN` 时 `/how-it-works` 自动返回中文；
- `/api/locale` 写入 cookie、跟随 `Referer` 跳回，并拒绝外部 `next` 目标；
- 英文默认输出保持不变（原有 39 个渲染测试全部通过）。

## 7.1 URL 前缀

`/zh-CN` 前缀、canonical 与 hreflang 已实现；语言切换 API 会把返回路径规范化到目标语言的前缀形式（例如从 `/zh-CN/about` 切到英文会回到 `/about`）。中间件只跳过真实静态资源扩展名与点开头目录：`/about.html` 因为扩展名是 `html`，与静态资源一样不进入中间件，404 页面的 canonical 会回退为 `/`；其他带点但不属于静态资源的路径（例如 `/about.foo`）仍按页面处理并获得指向自身的 canonical。

## 10. 已知边界

- 尚未处理复数规则、日期/数字的 locale 格式化；当前文案中没有必须依赖它们的场景。
- 验证控制台中的协议结果已随 locale 在服务端生成；哈希、ID 与时间戳保持原样。
- 解释组件位于 `app/components/explanation/`，按 UI 审计规则不直接依赖 i18n，因此通过 `t` prop 接收翻译函数。
- 历史里程碑是编辑内容而非界面文案，放在独立的 `milestone-copy.ts`，避免把 22 条史料塞进共享词典；新增条目未翻译时自动回退英文。
- Runner 可用性对象新增稳定的 `reason` 字段，页面据此选择词条；其他消费方仍可使用原来的英文 `label`/`detail`。
- 中文页面使用系统 CJK 回退字体（Geist 不含中文字形），后续可评估自托管中文字体对性能的影响。
- 语言 cookie 不区分 `__Host-` 前缀，因为本地开发使用 HTTP；生产环境仍限制为 `Path=/`、`SameSite=Lax`，HTTPS 下附加 `Secure`。
- 中文排版仍需要一次真实浏览器/移动端视觉检查；当前只能通过 CSS 断点与渲染测试覆盖结构。
- 首页两扇门（`Verify a claim` / `Start a target`）和收据页的验证面板同样**没有在真实浏览器里目检过**（2026-11-01）。已做的只是静态响应式审计：按 320 / 375 / 768 / 1280 四个宽度逐条核对断点规则、容器宽度、横向溢出、对比度与点击区域（静态计算，非浏览器渲染），并由 `tests/ui/responsive-surfaces.test.tsx` 固定——两扇门在 ≤760px 收成单列，收据边界与验证面板在 ≤1020px 收成单列，长标识符 `overflow-wrap: anywhere`，小字号标签对比度 ≥ 4.5:1。真实浏览器下的汉字断行、字重渲染、触摸滚动与软键盘仍未验证。
