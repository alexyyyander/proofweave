# 研究能力受控开放验收方案（2026-10-20）

状态：准备稿；不授权生产写入、执行、创建付费资源、发送链上交易或恢复定时任务。
当前组件和门禁见 [发布状态](releases/2026-10-20-release-state.json)。

## 目标与现有证据

从当前健康且暂停的基础设施，依次取得：隔离环境完整贡献链、一个受控 Runner 结果、
真实 Person A 的有界研究、不同 Person B 的独立评审、可公开重验的 Contribution Receipt，以及一份 Nile 存证。
每个阶段独立记录通过证据，后一个阶段不能借用前一个阶段的通过结论。

已具备正式域名/登录/只读 MCP、0049 账本、PR #162 签名与 CI、暂停 Runner，以及历史一次 Lean 成功运行的证据。
PR 的代码批准不是数学独立评审；两个 GitHub 账户也不自动构成两个独立研究 Person。
历史 Run 的一次投递额度已消费，不能作为新增执行的授权。

## 执行前必须填写的窗口记录

- 发行负责人、Runner 操作人、研究 Person A、独立评审 Person B、事故恢复人及窗口时间；角色可兼任，但 A/B 必须满足协议的不同所有者要求。
- 各组件完整 SHA/摘要、Worker/deploy/build ID、模板不可变 build、工具链/Mathlib、数据库指纹和完整迁移身份。
- 具体公开目标与 problem revision、Attempt、owner 批准的 Bundle/hash、对象清单、唯一 Run/idempotency ID；这些值当前均待拟定与核验。
- 固定 CPU/墙钟、内存、磁盘、输出、费用上限、一次投递次数和最大并行度；不沿用旧 Run 授权。
- 写入开放的具体 surface 和身份范围、允许产生的研究/评审/Receipt 数据，以及冻结和恢复的具体验证方法。
- 若验证 Nile：固定网络、账户/合约、允许公开的摘要载荷、最大测试币消耗及确认数；默认不启动循环 tick。
- 具体执行范围获准后才能实施。本准备稿本身不改变任何运行开关。

## 阶段一：隔离环境验证完整贡献链

1. 使用有明确资源授权的非生产 origin 和独立 staging 数据库；不复制生产密钥或私有研究数据。
2. 部署审核后的当前 schema 和组件组合；数据库按 reviewed SQL 校验至 0049。
3. 新版校验器审核通过后，运行真实 Lean、独立重放、评审和签名回执链。
4. 核对负例：错数据库、错来源、旧/未知迁移、相同所有者评审、无效签名、越界写入及重复事件都必须拒绝。
5. 保留匿名化证据，清理测试令牌和临时资源；隔离测试通过不构成生产或独立人类研究验收。

## 阶段二：生产 Runner 的单 Run 验证

前提是 G0–G3 已解除、具体 Run/Bundle/资源预算另行获准，且 participant/MCP 写入仍冻结。

1. 只读记录队列、活跃租约、目标 Run、账本和版本；确认没有其他消费者或写入者。
2. 在执行关闭时配置精确 `RUNNER_ONLY_RUN_ID` 和 `RUNNER_MAX_DELIVERY_ATTEMPTS=1`，逐项回读并固定 deploy SHA。
3. 经已批准的正式控制面创建/入队该一个 Run；不直接编辑数据库状态，不放开普通队列。
4. 临时启用该消费者并发送批准范围内的一次 wake。固定标签必须解析到已审核 template/build；不创建新模板。
5. 验证网络隔离、工具链、工作区签名树、租约围栏、Lean accepted、四项检查、结果签名、输出哈希及 acknowledged 终态。
6. 任何失败均停止，不自动追加投递。无论结果如何都恢复执行 false，保持 Run 限制，必要时重新暂停部署并回读 HTTP 200 / paused。

退出条件是该唯一 Run 的真实终态及无凭据证据；不声称贡献回执或数学新颖性通过。

## 阶段三：有界研究写入

1. 先证明指定 Person/Agent/Attempt 的限制在实际 participant/MCP 写路径生效，其他身份仍被拒绝。
2. global 当前已是 read_write；不要把重复打开 global 当作新门禁通过。
3. 逐个 surface 开放并观测，一次仅改变一个门禁。未到的 surface 保持 read_only；Runner 保持精确 Run 限制。
4. Person A 通过正式登录、授权 Agent、固定目标、批准 checkpoint/Bundle，完成批准范围内的研究链。
5. 检查所有状态迁移可持久化、幂等，越权路径拒绝；窗口结束恢复 participant/MCP read_only 和 Runner 暂停。

若只能按整个 surface 打开写入，先暂停在本阶段，提交细粒度门禁实现和审核，不能直接向所有参与者开放。

## 阶段四：真实独立评审与回执

1. 确认 Person B 与 A 的协议所有者不同；连接 review-scoped Agent，领取同一 Bundle 的正式 assignment。
2. 完成所需独立重放并签署 claim-specific 决策。代码 PR Approve、本地模拟评审或仅检查 Lean 日志都不能替代该证据。
3. 仅在所有必需评审和同一 Attempt/Bundle 的其他门禁满足后，按正式协调器签发 Receipt。
4. 从公开验证入口检查发行者签名、内容摘要、Person/Agent/委托归属、评审所有权分离和依赖关系。
5. 保存完整可重验结果；不得将测试身份或历史回执冒充本次贡献结果。

## 阶段五：Nile 存证与最终冻结

1. 另行确认固定测试网、固定摘要载荷、费用上限与发送范围；本方案不授权交易。
2. 仅提交批准的 Receipt/批次承诺摘要，不上传私有研究源码或凭据；以人工单次流程替代定时任务恢复。
3. 核对交易 ID、合约事件、批次根、Merkle 包含证明和既定确认数，再从公共入口回验。
4. 记录结果后保持研究写入、Runner 执行和定时任务冻结。存证不证明数学正确性或新颖性。

## 停止与恢复

- 身份、来源、迁移、签名、权限、队列、资源或隔离任一异常：停止后续动作，冻结对应 surface 和执行。
- 保留失败 Run、事件、死信、Bundle 和签名结果，不删除证据、不重写账本，不用直接 SQL 修饰终态。
- 回退使用当前已验证的 Runner `13c0795` 与已记录的 Cloudflare 版本，不将缺少 0049 的旧 Runner 当作可用回退版本。
- 生产 Turso 不重建、不回退迁移。涉及恢复数据时另走已审核的备份/恢复流程。
- 自动部署维持关闭，定时任务不自动恢复；每个阶段都记录开关回读与最终暂停健康证据。
